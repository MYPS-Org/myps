# MYPS changes since v2.0.8-project-groups-add-projects-and-more (not yet released)

## Multi-Year: planning projects reach the annual programs, PIP, imports and saved totals

- **Propose to RBP / UBP** on a project's page sends a New or Ongoing RDIP or UDIP project into an RBP: an RBP for the RDIP's region, or a UBP (an RBP program whose Data Security is the UDIP's UPMO cluster, or the UPMO). It creates a BP project in that program, with the project's description, Category and location, one Civil Works component holding that year's planned cost, and the project's MY ID as its **Multi Year ID**. The dialog asks only for what a planning project does not have: Operating Unit, Tier, Origin, Originating Agency, Implementation Mode, Emergency Mode, ROW Available, Feasibility Study and Detailed Design. Funding and locations are added afterwards on the project in Programs. A New project becomes **Potential**.
- Proposing is refused for an approved program, a program that is not at the RBP stage, a year with no planned cost, a year before the project's Start Year, a project already proposed for that year or waiting for the GAA, and a project without Province, City / Municipality, Legislative District, District Engineering Office, Implementing Office or Region Wide ("An annual project needs the ... Add them on this project's page (Edit Project) first.").
- **The Multi Year ID follows the project through the annual programs.** Keep it on the project when it moves on to BP, NEP and GAA: it is how MYPS recognises the planning project in those programs. The project page's new **Annual Programs** section lists every program holding it, with the stage and that year's amount.
- **When a GAA or GAA-R is approved, the portfolios update themselves** (also when a GAA moves on to GAA-R): a Potential project in the GAA becomes **Ongoing**; one not in it goes back to **New** with the next year as its Start Year (or becomes Ongoing if it was implemented in another year's GAA); a New project whose Start Year has come moves to the next year; and a GAA project whose Multi Year ID matches no planning project joins that term's **PIP** as Ongoing. Running it again changes nothing. Program Details shows what changed after the save. **The approval itself never waits on it or fails because of it**: if the update cannot finish, the program is still approved and a notice says so.
- **The update runs again when a Non-Implementable revision, or a Termination with No Disbursements, is approved**: a project whose only GAA entry was withdrawn goes back to New with the next Start Year.
- **GAA Updates** (AUC and Admin), on the Portfolios page, lists every update with what it changed, and **Run GAA Update** repeats it for a year with an approved GAA or GAA-R.
- **Add Project to PIP** (PPC and Admin), on an open PIP, adds a New or Potential project from any RDIP or UDIP. It needs an MCA Score from 0 to 100, copies the project's cost into its **Original Cost**, which never changes, and shows which RDIP or UDIP it came from. **Set PIP Cost** (PPC and Admin) changes its PIP cost; the change is kept in the project's History.
- **Import Projects** on an open RDIP or UDIP: download the template, fill one project per row, and upload it. Amount 1 is the Start Year's planned cost, Amount 2 the next year's, and so on, for as many years as needed. A blank amount before a filled one, a zero amount or a value not in the template's Lists sheet is refused with the row number; the other rows are still added, each as a New project with its own MY ID.
- **Saved Totals** tab on every portfolio: the planned, proposed and approved cost of each term year, with the year's budget ceiling, saved when a term opens or closes, after each GAA update, and with **Save Totals**. Each year counts once: Approved when an approved GAA or GAA-R of that year holds it, else Proposed when an annual program of that year holds it, else Planned. Saved totals are never edited.
- Each project's **History** in a portfolio now also shows start year and PIP cost changes, and which changes the GAA update made.
- **Not in this release:** locking past years, Multi-Year Costing Changes rules, the TRIP, MTPIP and CIP reports, and converting the old RDIP and PIP programs into portfolios.
- **For administrators:** two more database updates, run by hand once on each server after the Multi-Year ones: one adds the tables for proposals, updates and saved totals, the other gives the groups their starting permissions for these actions in Edit Group.
- Internal: a revision test that read an older version of the packaging rule now checks the shared rule it moved to. Nothing visible changed.

## Multi-Year: RDIP, UDIP and PIP portfolios over six-year terms

- **A new Multi-Year menu in the sidebar opens Portfolios.** An RDIP is the multi-year plan of one region, a UDIP of one UPMO cluster, and the PIP the national plan. Each covers a fixed six-year term, for example 2023–2028.
- **Create Portfolio** (AUC and Admin) makes an RDIP for a region, a UDIP for a UPMO cluster, or the PIP, for a term start year. Only one portfolio exists per kind, owner and term, and terms of the same owner cannot overlap. The UPMO clusters offered are the cluster offices in MYPS's office list.
- **Add Planning Project** puts a project into an open RDIP or UDIP: description, Category and Sub-Category, location, horizon (Short term 3 years, Medium term 6 years, Long term open-ended), Start Year and optional End Year, one Civil Works component with its infrastructure type, dominant type of work and physical target, and its planned cost for each year. It gets an MY Project ID when saved, for example MY00700026VS.
- A planned cost of zero, a year entered twice, a year before the Start Year or after the End Year is refused. **A year past the horizon is saved, with a warning.**
- **One record per project.** The project page shows its yearly costs, each year marked Planned, and every portfolio it belongs to. Each portfolio keeps the project's own status, start year, cost and planning fields: Basis for Implementation, NEDA Project Status, Readiness Level, RDP Results Matrix outcomes (one output each), Tier and MCA score.
- **Project status in a portfolio:** a project starts as New. A coordinator can set New to Cancelled, and Ongoing to Completed or Cancelled; any other change is refused. Completed and Cancelled projects can no longer be edited in that portfolio. The Start Year can be changed only while the project is New, and Category and Region cannot change once saved, because they are part of the Project ID. The project's original cost never changes.
- **Budget Ceilings** tab: the budget ceiling for each year of the term, beside the planned cost of the projects that are not cancelled.
- **Open Next Term** (AUC and Admin) opens the next six-year term. Every project that is not completed or cancelled is carried into it with its fields, and the old term becomes closed and read-only. Portfolios are never deleted.
- **Who sees which portfolio follows the user group's Project visibility**: All projects sees every portfolio; Own region sees that region's RDIP; Own district office sees the RDIP of the office's region. A new choice, **Own UPMO cluster**, sees that cluster's UDIP, or every UDIP for the UPMO itself; for projects it works like By program Data Security. **The PIP is seen with All projects, or with the new Show PIP permission** (given to PPC).
- **Code Tables → Multi-Year** holds Basis for Implementation, NEDA Project Status, Readiness Level and the RDP outcomes and outputs, each with Valid From / Valid To years and Active. A value is retired, never deleted, and a value in use cannot be renamed. The lists start empty.
- **Not in this release:** locking past years and the TRIP, MTPIP and CIP reports. Proposing into an RBP, Add to PIP, the update after a GAA approval and importing are in the section above. The RDIP and PIP stages of the Programs list are unchanged.
- **For administrators:** two database updates, run by hand once on each server: one adds the Multi-Year tables, the other gives the groups their starting Multi-Year permissions in Edit Group. On a server where Project visibility was already set up, Own UPMO cluster needs a third update (it now says which update to run first when that one is missing); until it runs, Edit Group refuses that one choice with "Own UPMO cluster cannot be chosen on this server until its database update (Migration.GroupProjectScopeCluster) has been run. Ask your administrator."

## A year's MYOA approval date is kept when a program moves to its next stage

- **A component cost year's MYOA approval date is now copied when a program advances to its next stage**, and when a deleted project is restored into the current stage. Before, the copy in the new stage had no MYOA date, so the AIP no longer marked that year MYOA.
- Projects that already advanced keep the stage copies they have; this applies to advances made from now on.

## An approved RBP program locks its projects

- **The projects of an approved RBP program can no longer be updated**, as intended: Update Project is refused with "Project details cannot be updated. The project is already locked". Before, the check never matched, so the server accepted the update.

## Each user group has a Project visibility setting

- **Which projects a group's members see is now a setting of the group:** **Project visibility** in User Management → User Groups (Add Group and Edit Group), also shown in the User Groups list. The choices are **All projects**, **Own region**, **Own district office** (both from the member's Plantilla Office), and **By program Data Security**, the existing rule that uses Apply Filter and each program's Data Security Access.
- **Nobody sees anything different today.** Each group starts with the visibility it had: AUC and DPD Admin all projects, RPC own region, DPC own district office, every other group By program Data Security. Before, this was fixed by those four group names and could not be given to another group.
- A user in several groups sees the widest: All projects wins, and Own region and Own district office add up. A member whose Plantilla Office does not fit Own region or Own district office sees no projects, as before.
- The new groups PDA, PDC, PPC, RPO, UPC and VIEW start at By program Data Security. With Apply Filter on, that can show them no projects at all, so set each one's Project visibility to what the role needs.
- **DPD Admin can now be renamed.** DPC, RPC and AUC still cannot: the revision approval steps use their names (DPC submits, RPC endorses, AUC approves).
- **For administrators:** the setting needs a database update, run by hand once on each server like the others. Until it runs, every group keeps the visibility its name gave it, and Edit Group refuses a change of Project visibility with "Project visibility cannot be changed on this server until its database update … has been run."

## User groups can do what the client's access matrix gives them, and buttons they cannot use are hidden

- **Each user group's permissions now follow the client's access matrix**, for AUC, DPD Admin, PDA, DPDC/PDC, PDC, PPC, RPO, RPC, DPC, UPC and a new **VIEW** group. The User Manual's new section 5.8.4 lists what each group can do. Every group can view programs, projects, project groups, revisions, future infrastructure and reports.
- **RPC and DPC no longer create, edit, delete or move programs to the next stage, manage project groups, use Restrict Publishing or run the AIP reports.** DPC also no longer uses Allow Publishing. In the matrix these belong to AUC, DPD Admin and PDA.
- **DPD Admin can now open Programs, Project Groups, Revisions, Code Tables and Infra Management**, and import, export and revise projects. Before, it held the program permissions but could open none of those pages.
- **DPDC/PDC can now open project details and the projects of a program.** Before, those pages failed for that group. It no longer has User Management, Code Tables, future infrastructure editing or the program actions, which the matrix gives to others.
- **Deleting a project works for every group that may delete.** The delete first asks for a preview, which only AUC and RPC were allowed, so DPC, DPD Admin and DPDC/PDC could not delete a project.
- **The AIP reports are for AUC, DPD Admin and PDA.** Other groups do not see them under Report Type, and a request for one is refused with "Your user group cannot generate the AIP reports." Every group can now open the Reports page for the other reports.
- **Buttons your group cannot use are hidden**: Add Program, Update and Proceed on a program, Publish Program, Add Project, Batch Actions entries, Import, Update and Export Projects, Revise Project, Update Project, Supporting Documents, project group Add, Update and Remove, and the Add, Edit and Delete buttons of Infra Management. Before, they were shown and answered "You do not have permission…" when clicked. A program or project your group cannot edit is shown read-only.
- Unchanged: the Admin and SD groups, Lump Sum, and the approval of revisions (RPC and AUC). Matrix rows that MYPS does not have yet, such as Synchronize PIP, Conduct MCA and Archive / Restore Program, are not applied.
- **For administrators:** none of this is fixed in the application. Every item above is a permission of the user group, set in **User Management → User Groups → Edit Group**, and the pages, buttons and AIP reports follow it as soon as the user reloads the page. A database script gives the groups their starting permissions; it is run by hand once on each server, like the other database updates, and names every change it makes. Running it again would undo changes made in Edit Group since.
- **Lump Sum and Code Tables are no longer hidden from DPC and RPC by group name.** Like every other page, they follow the group's permissions in Edit Group (neither group has them by default). The Infra Management **Import** button follows the group's permission to add future roads, also no longer a fixed list of group names.

## Sign-in can be limited to office computers, and the permission lists match who can sign in

- **For administrators: sign-in can be limited to computers under the organization domain.** A server's settings can now list the allowed domains. Sign-in from a computer whose name is not under one of them is then refused with "Sign-in is allowed only from a computer under the organization domain. Use your office computer, or ask your administrator.", and the attempt is recorded in the login history. It is off unless set, so nothing changes for anyone today. Before turning it on, check that the office computers' names reach that server.
- Before, every page checked "Hostname not found in the ip, make sure your working pc is under the organization domain.", but that check could never refuse anyone. It is removed.
- **For administrators:** the lists of who holds which permission now leave out the two accounts that cannot sign in, as the user list already did. Nothing changes for any user. A database script applies this on each server by hand, like the other database updates.
- Internal: every deployment now type-checks the front end first and stops on a type error. Nothing visible changed.

## User Management: user details stay as PIS gave them, groups keep their hidden permissions, and Sync asks first (S04-TC025, TC026, TC028, TC030)

- **Saving a user in Edit User no longer changes their office.** The name, email, region and office come from PIS and are read-only in Edit User, but a save replaced the office on record with the user's region, for every user whose office is not their regional office. A save now keeps what is on record. They change only when you type a new Employee ID and click the search button. A changed Employee ID that was not searched is refused with "Click the search button to look up the new Employee ID in PIS before saving.", and a recorded Employee ID cannot be cleared.
- **A user's login (User ID) cannot be changed.** Before, a changed login could be saved and the user's groups no longer matched their account.
- **Your own account is locked in Edit User.** Its Employee ID, groups and status are disabled with a note, and its Delete button is disabled. Another administrator has to change them. Before, the dialog let you try and the save was refused.
- **Add User needs at least one user group.** "Select at least one user group." A user without a group could not sign in and did not appear in the Users list.
- **Saving a user group keeps the permissions the dialog does not list.** The dialog shows only the permissions of controllers and pages that belong to a module. Saving used to remove every other permission the group had, for example the PIS employee lookup that DPD Admin needs.
- **A group you belong to cannot lose session validation either.** Your own group already could not lose its User Management access; a save that would take away the sign-in check every page needs is now refused too.
- **A group name cannot contain double quotes or backslashes, and can be at most 100 characters.** Such a name broke the group list of every user in that group. A name with spaces before or after it, such as " Admin", is refused as a duplicate instead of failing.
- **The DPC, RPC, AUC and DPD Admin group names are shown read-only in Edit Group**, with the reason. They already could not be renamed; the dialog now says so before you save.
- **Delete Group says up front that a group with members cannot be deleted**, names how many members it has, and stays disabled. Remove the group from their accounts in the Users tab first. Before, it let you type DELETE and then refused.
- **Sync API and Sync Routes ask for confirmation**, then reload the module list. **Sync Routes no longer removes a page a user group still has.** It used to remove every route the open page did not know, so a browser tab opened before an update could take pages away from groups. Such a route is now kept and named, with "Kept because user groups still have them: …". A sync with no routes is refused.
- **Module Name is read-only when you edit a module.** A module cannot be renamed; before, the name could be typed over and the save was then refused with "Module Id and ModuleName do not match."
- **A deactivated or deleted user can no longer run or download reports.** The reports were open to anyone whose sign-in had not yet expired.
- The Users and User Groups counts at the top refresh after an add, edit or delete, and the group lists in Add User and Edit User are in alphabetical order.
- Not changed: which groups may manage users. Every group that has the User Management page and its actions can still add users, edit groups and assign any group, including Admin. That is set in each group's permissions.
- User Manual: section 5.8 (version 3.29) and the page's own help describe the above.

## Revisions: a revision type is refused at a PCMA status the URD does not allow (S03)

- **A Modification is no longer allowed when the project's components are Completed or Terminated.** The revision page shows "Modification is not allowed because the Project Component has been Completed/Terminated.", the message the URD gives. Before, the revision page opened and nothing could be changed.
- **Change in Authority to Implement is allowed only while the project's components are Not Yet Started and Not Packaged.** At any other status the revision page says so and names the project's status.
- **A refused revision shows a notice with Back to Project Details.** Before, the page showed "Loading project data..." and then returned to the project without explaining why.
- **The PCMA and package status are read by MYPS when a revision is submitted or resubmitted.** Before, the page sent them, so a page left open while the status changed in PCMA could submit under the old status.
- A reason that has no Revision Field Permission for the project's status is refused in plain words: "This revision reason is not allowed while the project's components are … and …". Before, it read "Revision rule does not exist for PCMA_Status: …".
- Unchanged: on Change of Implementing Office while Not Yet Started and Not Packaged, the revision page lets you change the Implementing Office, as Code Tables sets it. Project Details itself stays read-only at GAA-R; the fields are edited on the revision page that opens after Revise Project.
- Not done yet: the URD's allowed statuses for the other revision types. They follow their Revision Field Permission rows until that list is applied.

## Reports: the RBP Summary covers a program at any stage, the AIP shows physical targets, and errors read plainly (S08-TC002, TC003)

- **RBP Summary Report and RBP Summary Report with Tier now list the program you tick, at the stage you choose.** Before, they only read programs that had an RBP stage, so a program at BP, or one that went from BP straight to NEP, gave an empty summary while the RBP report for the same program had projects. Their project counts and amounts per category now match the RBP report.
- **The AIP reports show a Major Item of Work that has no work location.** Its Type of Work and Target Unit now print, with a Physical Target of 0. Before, all three were blank while the cost still printed. This applies to AIP Official, AIP Executive and AIP Official without LD. To report the real target, add the Major Item's work locations.
- **A report that fails now shows only the reason.** Before, the message appeared with its technical wrapping, for example {"Message":"..."}.
- Planning Engineer, Approved By and Reviewed By are optional on the RBP and RBP Summary reports. Left empty, the signature block shows only the role titles. A server whose report service is older than 23 October 2026 still asks for the three names: "Report-level parameter(s) not supplied: @PlanningEngineer, …". The report service has to be updated on that server.
- Regional Office, Category and District Engineering Office stay optional for Extract PCMIOW and Extract PC.
- **For administrators:** these report changes are not installed by a normal deployment. The four report procedures and the report service have to be updated on each server by hand, as the report service guide describes.

## Lump Sum: itemized projects import into any program, and Sub-Category offers only its Category's values (S07-TC003-P001, TC007-P002, TC001-P002)

- **Import Itemized Projects no longer fails when the program's projects have moved past BP.** The import stopped with "Project ID generation failed: still colliding after 3 attempts". A project created at BP keeps its number when its program moves on (BP01100016LZ becomes P01100016LZ), and the numbers for new projects did not take those into account. A new Project ID now skips every number that a project already has, with any of its BP, P or MY beginnings. This also applies to Add Project and the Program import.
- **Sub-Category no longer shows "PROGRAM OF WORKS/BUDGET COST" on an empty Add Lump Sum Project form.** That entry stands for "no Sub-Category", but the box showed it as if it were chosen. It is no longer offered on the Lump Sum, Project or Modification forms.
- **Sub-Category stays locked until you choose a Category.** It says "Select a Category first", and then lists only the Sub-Categories that Category permits for the program's year, as the Project form does. Before, it listed every Sub-Category, and most of them were refused when you saved.
- **Two Sub-Categories that share a name now show their Infrastructure Type after it**, for example "Basic Infrastructure Program (BIP) - Coastal Roads to augment Resiliency of Coastal Communities (Roads)" and "... (Bridges)". The same applies to the SIPAG pair, on the Lump Sum, Project and Modification forms. The Excel import still uses the name without the type.
- **Pointing at a dropdown shows its full value.** Long Sub-Category names are cut off in the box.
- **A Lump Sum search that finds nothing now says "No Lump Sum Projects match your filters."** and offers **Clear filters**. Before, it said "No Lump Sum Projects found." and offered "Create the first one", as if there were none at all.

## Infra Management: new IDs reuse free numbers, a bridge must start on its road section, and Import is for PS Admin (S06-TC003-P001, TC010-P001, TC015, TC016)

- **New Road, Section Road and Bridge IDs take the lowest free number.** Before, MYPS took the highest number in use plus one. The IDs migrated from RBIA were assigned by hand and already run as high as FS97844 and FB97614, so only about 2,000 numbers were left, and the number of a deleted road, section or bridge was never used again. Now the unused numbers are filled first, and a deleted item's number is used again. A section or bridge number that a project refers to is never reused.
- **A bridge's From Chainage must lie on its road section.** Add Bridge and Edit Bridge refuse a From Chainage beyond the section's Length, for example "From Chainage must be between 0 and 520 m, the length of road section FS00016LZ." The bridge itself may run past the end of the section.
- **A road section cannot be made shorter than where one of its bridges starts.** For example: "A bridge on this road section starts at 500 m, so its Length cannot be less than 500 m."
- **From Chainage is in meters.** The bridge dialog labelled it in kilometres. The section list in that dialog and the Delete Bridge and Delete Road Section dialogs also said km. All of them now say meters, as the lists do.
- **District and regional users (DPC and RPC) no longer see the Import button.** The RBIA, AAMS and IOMS imports are for PS Admin. They run in the GIS service, so the button is the only place MYPS can limit them.
- Each import still reports its own result when it finishes, and the RBIA import names how many roads, road sections and bridges came in.

## Project Groups: saves are confirmed, and the saved name is what you see (S05-TC002, TC003, TC004)

- **Update on Project Group Details now says it saved.** The message "Project Group '<name>' updated successfully." appears. Before, nothing was shown, so there was no sign that the change had been saved.
- **Add Project Group confirms the save too**, with "Project Group '<name>' added successfully.", and then opens the new group's details page.
- **The Name and Description are shown as they were saved**, without spaces before or after them, and the Add Projects and Remove dialogs show that saved name.
- **A name that a deleted project group had is refused with a message that says so:** "A deleted Project Group already used this name. Please enter a different name." Before, it said "Project Group Name already exists." even though no such group is in the list. The name of a deleted group still cannot be used again.
- If you open another project group while the details page is still loading, the page now shows the group you opened last.

## Modification: a revision with a blank Component Cost date can be submitted, and a year added on Re-Submit keeps its Year (S02-TC003-P001)

- **Submit Revision Request and Re-Submit Revision now work when a Component Cost year row has no Start Date or End Date.** Since the dates became optional, such a row made the request fail with an error. The same happened before for a project whose dates were blank to begin with, for example one brought in by Import.
- **A Component Cost year row added before Re-Submit Revision now keeps its Year.** Before, the row was saved without its Year.

## Component Cost: Start and End Dates are optional, and an End Date can run into the following year (#2)

- **Start Date and End Date are no longer required.** A year row in the Component Cost dialog can now be saved with either date, or both, left blank, for when the implementation schedule is not set yet. Before, Save stopped with "Please select a Start Date." or "Please select an End Date." This applies on the project page and in Modification.
- **Each year row's End Date can run up to December 31 of the following year**, because the funds stay valid for two years. For example, a 2029 row can end as late as December 31, 2030. Before, the End Date had to be in the row's own year. The Start Date still has to be in the row's year.
- **Date and Year problems now show as a message at the top right when you click Save**, on the project page and in Modification, for example "End Date must be between 01/01/2029 and 12/31/2030." Before, the browser showed its own pop-up under the field ("Value must be ... or earlier."). A date that is entered is still checked: the Start Date must be in the row's year, the End Date cannot be before the Start Date, and the Year must be within the program's years.
- Not fixed yet: **Auto-fill** of the component Description for Local Infra. The description comes from the GIS service, which is outside this release.

## Code Tables: a refused save shows only its reason, and the revision form names its Reason (S04)

- **When Code Tables refuses a save, you now see one message: the reason.** Before, a second message followed it. For example, adding a Category whose amount range overlaps an active one showed "The range … overlaps with active category …" and then "Failed to add category.", which read as if something else had gone wrong. This applies to every Code Tables screen: add, edit, delete and Active / Inactive.
- The general "Failed to …" message still appears when the server cannot be reached or gives no reason.
- **The revision form's header shows the Reason by name.** Before, it read "Modification Reason: 12", the reason's number. It now reads, for example, "Modification Reason: Altered Site Conditions".

## Code Tables: Validation Dates are saved and set when revisions can be requested (S04-TC016)

- **Validation Dates are now saved.** Before, the screen showed sample rows for 2016 to 2024, and Add, Edit and Delete only changed the page: a reload brought the samples back.
- **A new revision request is accepted only inside its funding year's window.** For a project whose program year has an active range, Request Revision outside the dates is refused with *"Revisions of FY \<year\> projects can be requested from \<start\> to \<end\>."* A year with no range, or an Inactive one, has no limit. A request returned For Correction can still be resubmitted.
- One range per funding year; the Start Date cannot be after the End Date. The **Window** column shows **Open**, **Not open yet** or **Closed**.
- The list starts empty: the old sample rows were placeholders. PS Admin enters the real ranges.
- Internal: the database needs `Migration.RevisionValidationDates.2026-10-30.sql` once per environment. Until it runs, the screen shows no ranges and nothing is enforced.

## Code Tables: edits no longer switch rows off, and rows in use are protected (S04)

- **Editing a Revision Rule or an Origin no longer makes it Inactive.** Before, a rule edited on the **Rules** screen was switched off and disappeared from the list, and its revisions could no longer find their editable fields; an edited Origin disappeared from Add Project. A new Origin is now created Active too.
- **Every changed field is in the history.** An edit that changed two fields used to record only the last one, and Sub-Category (Thrust) changes were recorded under Category.
- **Deletes and changes that would break saved data are refused, with the reason:** a Revision Header, Category, Reason or Rule still in use; moving a Reason used by requests to another header (those requests then failed with "Revision Reason not found"); a Cost Type projects use (it used to fail with a generic database error); an Infrastructure Type a Type of Work lists; removing an Infrastructure Type from a Type of Work that Major Items use with it; changing the source organization of a Funding Agreement in use (its funding lines showed a blank Agreement).
- **Program Stages can no longer be added.** A stage added here could not be used: a program at it could not be opened. Edit a stage's Description or set it Inactive.
- **Adding a Type of Work asks for its Target Unit and a Max.** Before, it was saved with Target Unit "0" (the form showed "Physical Target (0)"), and a blank Max became a limit of 0.
- **Checks on save:** a Sub-Category (Thrust) needs a PAP Key and a description, and its Valid From cannot be after its Valid To; a Category needs a name, and its Min Amount cannot be above its Max Amount; an Origin needs a name.
- The Sub-Category PAP Key, the Agency NameId and a Rule's Reason are shown read-only when editing: changes to them were never saved.
- Setting a Funding Source Active or Inactive no longer changes a blank Nature to Local, and two people adding to the same table at once no longer get the same Id.
- In a Modification, choosing another Type of Work for a Major Item whose Infrastructure Type has since been set Inactive is accepted; it was refused with an error about the Infrastructure Type.
- Internal: two exception-report endpoints in Program Details built their query from the Program ID as text; they now pass it as a parameter.

## User Management: older accounts can be edited, lists page correctly, and no one can lock themselves out (S04)

- **Edit User saves for older accounts.** Accounts saved without an Employee ID, or whose office has no region on record, could not be saved: Save was refused with "Employee ID is required" or "Invalid Region Code". They now save, and the region already on record is kept.
- **Edit User says when a user has no Employee ID on record** (S04-TC028), and how to add it: enter the Employee ID and click the search button to fill in the details from PIS. View User shows "Not recorded" for such a user.
- **The Users, User Groups and App Modules lists page correctly.** Page 2 and later used to show page 1 again. The lists now reload after Add, Edit or Delete.
- **Deleting a user you just added deletes that user.** Before, a newly added user was given another user's number until the page was reloaded, so its Delete removed someone else. Delete is now also refused if the user shown is not the one on record. The same applied to a newly added App Module.
- **The User Group filter matches the group exactly** (S04-TC027). Filtering by "Admin" no longer also lists the members of "DPD Admin".
- **You cannot lock yourself out.** Your own account cannot be set Inactive or have its groups changed, and your own group cannot lose its User Management access. Ask another administrator.
- **Add User needs an Employee ID, and two users cannot share one.** Changing the Employee ID after a search now clears the details found, so a user is never added under someone else's Employee ID.
- **The DPC, RPC, AUC and DPD Admin groups cannot be renamed.** What their members see depends on these names.
- **Filter Group by Permission Name works** (S04-TC029). It was ignored, so the full list came back. It now lists the groups granted a permission whose module, controller, action or page name contains the text, and Clear Filters works when only Permission Name is filled.
- The Add and Edit Group dialogs explain Apply Filter: a user in several groups is region-filtered only when all their groups have it on. Delete Group no longer shows its error message twice.
- **Security:** the PIS employee lookup and the raw projects export could be called without signing in. They now need a signed-in user: the lookup needs User Management access, and the export only covers programs the user can open.

## Users limited to their region see only their region in search, Project Groups and Import (S04-TC031)

- **Global Search** no longer returns other regions' projects or programs to a user whose groups have Apply Filter, or to a DPC or RPC user outside their offices. Before, searching by Project ID, Alternate ID, Description, UACS or Program Name listed them, even though opening them was refused.
- **Project Groups:** such a user cannot find another region's project to add to a group, and filtering the groups by its Project ID finds nothing. A group's details and its count in the list show only the projects they can open.
- **Import, Update and Export** of another region's program are refused with "Access Denied". Before, they were accepted when the Program ID was sent to the server directly. The same applies to the server's program search, which the screens do not use.
- Users whose groups don't have Apply Filter, such as administrators and AUC, see everything as before.

## Code Tables: setting a value Inactive no longer blocks the projects that use it (S04-TC001, TC002, TC007)

- **An Inactive Infrastructure Type or Type of Work no longer locks a project.** Before, once one was set Inactive in Code Tables, every save of a project that used it was refused, and its Type of Work and Unit showed blank. Now the Major Item keeps showing it and the project saves. It is only left out of the list for new Major Items, and a component whose Major Item uses it can still be deleted.
- **The same for a Funding Agreement or Funding Source:** a funding line that already uses it keeps showing it and saves. It is not offered for a new funding line, and a new Lump Sum cannot use it.
- **An Origin or Agency can be set Inactive even while projects use it.** Before, Code Tables refused with "In Use". Those projects keep showing and saving it; it is not offered when you change a project's Agency.
- **A Category or Sub-Category (Thrust) can be set Inactive while in use**, and a project whose Category is no longer valid still saves as long as its Category is unchanged. A Category or Thrust in use still cannot be renamed.
- **Category and Sub-Category validity now follows the program's year, not today's date.** A project in a 2028 program is offered the Categories and Sub-Categories valid in 2028.

## User Manual: sign-in error message brought up to date (S01-TC001-P002)

- User Manual only. The app is unchanged.
- The Login section and the message tables now quote the message the app shows when a sign-in fails: "Unable to sign in. Please verify your User ID and password and try again." They still quoted the older "Invalid credentials" message.

## Changelogs show the newest change first

- **Within a release, the newest change is now at the top.** Before, a release listed its changes oldest first, so the latest ones sat at the bottom of a long list.
- Quoted messages in *italics* and names such as Restore into &lt;stage&gt; now show as written. Before, they showed with their asterisks, or as `&lt;stage&gt;`.

## Program cost and project counts leave deleted projects out

- **A deleted project no longer counts toward its program's Cost.** Before, a project deleted at a stage after BP (one that can be restored) kept its cost in the program. Program Details and the Program list showed the old Cost until the project was permanently deleted, which past BP never happens. The Cost now drops as soon as the project is deleted, and goes back up when it is restored.
- **No. of Projects in the Program list and the Projects column of its stage rows no longer count deleted projects.** They now match the Projects table in Program Details.
- **Some older programs showed a different Cost in Program Details than in the Program list.** Their stages had been recorded out of order. When the program cost was updated, it updated an earlier stage instead of the current one. It now always updates the current stage, so Program Details shows the same Cost as the Program list.
- Internal: the database needs `Migration.ProgramCostExcludesDeleted.2026-10-29.sql` once per environment. It also updates the Cost of the programs this changes.

## Restore a project deleted at an earlier stage into the current stage

- **A project deleted before the program moved on stays deleted.** Proceeding to the next stage does not bring it back.
- **Deleted projects now also lists projects deleted at an earlier stage**, in their own section, with the stage each one was deleted at. A note explains that the program has moved on: restoring adds the project to the stage the program is at now, with the data it had when it was deleted, and the stages in between are skipped. For example, a project deleted at HGAB is restored into GAA.
- Click **Restore into &lt;stage&gt;** on a row, or tick several and click **Restore selected**. The project is back in the Projects table, and the program cost is updated. A BP Project ID becomes P, as it does when a program proceeds from BP.
- A project cannot be restored this way when it is published, when the program is Approved, when it is a Lump Sum project, or when its Project ID is now used by another project. The row says why.
- Batch Restore still restores projects deleted at the current stage, and its dialog now points to **Deleted projects** for the others.

## Permanent delete only at BP or RBP, and a Deleted projects list to restore from (S01-TC004-P002)

- **A project is permanently deleted only while it is still at the BP or RBP stage.** At any other stage, Delete and Batch Delete remove it from that stage only, and it can be restored. This now also covers a project added directly at a later stage (for example at NEP or GAA), which used to be deleted permanently.
- **A program can be deleted only while it is at BP or RBP.** A program that has moved on, or was created at a later stage, cannot be permanently deleted; the Delete button says why.
- **New Deleted projects (N) button in Program Details.** It lists the projects deleted at the program's current stage, with who deleted each one and when. Click **Restore** on a row, or tick several and click **Restore selected**, and they are back in the Projects table. You no longer need to type Project IDs into Batch Restore.
- **The delete message says only what happened.** A restorable delete reads *"1 project(s) deleted at the current stage; they can be restored from Deleted projects."* instead of starting with *"0 project(s) permanently deleted"*.
- **Project IDs are reused.** When a project is permanently deleted at BP or RBP, its Project ID is given to the next new project of the same kind. IDs starting with MY, and Lump Sum itemized projects, are not reused.
- Internal: the database needs `Migration.DeleteRulesAndProjectIdReuse.2026-10-29.sql` once per environment, for the ID reuse and the Deleted projects and Restore into stage permissions.
