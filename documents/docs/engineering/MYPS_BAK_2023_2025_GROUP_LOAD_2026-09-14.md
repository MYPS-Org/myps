## 1. Why

`myps_db_dev_200` was restored on 2026-09-10 from the 192.168.50.200 server and carried the **2024** program groups only. The Lump Sum projects the maintainer asked about — ids ending in `LS`, some holding a component "not of LS type" — are in the **2023** and **2025** groups, which the restore never received. They live in `MYPS_BAK`, the backup of the old system, in the old data model.

The instruction was to bring them across with the reference pipeline rather than a new script, whole program groups rather than the Lump Sum rows alone, 2023 onwards only, localhost only. `MyMYPS` is dummy data and was ignored.

The reference is the pipeline that produced `dev_200`'s 2024 data in the first place: the key convention (`ProgramPK = MP_<first-stage programid>`, `ProjectPK = ProgramPK_<projectid at first appearance>`), the literal string `'NULL'` in `ProjectType`, and the component-type **codes** where the application expects names are all its signature.

## 3. Two defects in the reference, fixed before loading

### 3.1 One component row per distinct yearly cost

`queries.build_project_component_cost_sql` selected the per-year columns (`cost`, `start_date`, `end_date`, `date_of_approval`) alongside a correlated `SUM` over all years and relied on `SELECT DISTINCT` to collapse them. DISTINCT cannot collapse rows that differ, so a component with *N* distinct (cost, dates) shapes became *N* component rows, each carrying the whole Total — and the per-year query then joined its rows to every copy.

Evidence, on `dev_200` as loaded by that form: **176,316** (revision, component) pairs with more than one live row, up to 27 copies, every copy with the same Total. `P00201118LZ`'s `CW1` in HGAB 2024 OO-1: 10 cost-stream rows, 9 distinct shapes, **9 component rows** of ₱2,673,766,590 each. The 53 duplicate Lump Sum components retired on the first migration run were this. The itemized children of the 2024 parents carry exactly two copies each, which doubles their parents' `ItemizedTotal` the moment they are linked.

Fix: `GROUP BY` at component grain, `Total = SUM(cost)`, per-year columns dropped from the query (they belong to the per-year loader). Verified on the 27-copy case: one row. `verify_component_grain.py` checks every loaded group for one row per pair and Total = source Σ cost — **161,756 pairs, all one row, all matching**.

### 3.2 The target's column names

The reference writes provenance as `DataImportProgramId` / `DataImportProjectId` / `DataImportComponentId` — the shape of `myps_db_migrated`, which its own `data_import_ids.sql` adds by hand. The application's database has a single `DataImportId` on the program, project, revision, stage and funding tables. The reference's answer for `myps_db_migrated` is `import_id_rename.sql`, which renames the columns; on the app's EF-mapped schema that would break the model.

Fix: `TARGET_COLUMN_MAP` + `to_target()` map frames at write time, and `target_column_name()` resolves the name on **reads** as well — the second half was missing at first and cost one run: `build_project_stages_sql` reads the revision's provenance column back to stamp the stage rows, and named it literally. The map lives in `queries.py` so writes and reads cannot disagree.

## 4. What was added

- **Itemization notes travel.** `build_project_notes_sql` copies `dbo.history` rows reading `'Itemized from Project: …'` or `'Cost reduced due to itemization…'` into `tProjectNotes` on the child's revision, at every stage, with a `NOT EXISTS` guard so it is repeatable. This is how the parent/child link — recorded nowhere else in the old model — reaches the target. `migrate_notes_for_programs` back-filled the three 2024 GAA-R programs already loaded (2,059 notes). `verify_itemization_notes.py`: 4,037 links, every one resolving to a loaded parent, 0 duplicates, 1 known source gap (`P00851066VS` has a note and no `dbo.project` row).
- **`steps_for_2023_2025_groups.py`.** Inline group config (no Excel), source and target as constants with a guard that refuses any host not loopback or this machine (`.env` names `192.168.50.200`), `SQL_ECHO` off, refuses to start if a group's `ProgramPK` already exists, `--notes-only` for the back-fill. Both engines use the `MYPS_BAK_DB_*` credentials because both point at localhost; the `MYPS_DB_*` pair is the remote server's and fails to log in here, which is the right outcome.
- **`rollback_program_group.sql`.** The reference commits per table per stage, so a mid-group failure leaves it half loaded and nothing else can undo that short of a restore. Deletes one `MP_…` group in dependency order; refuses an application-created key.
- **A program-cost overflow fallback.** `GAA 2023 CSSP as Approved` carries `program.cost = 300,585,464,920,206` in the source — 772× its own cost stream (₱389,179,466,579) and 1,900× its sibling stages — and it overflows `tProgramRevisions.Cost decimal(18,5)`. It is the only such row in `MYPS_BAK`. By the maintainer's decision, a program whose stored cost reaches the column ceiling gets `SUM(projectcoststream.cost)` instead — derived from its own rows, and the same basis `pRecomputeProgramCost` uses when the app recomputes this column, which it does. The substitution is logged with both figures; it fired exactly once.

## 5. What went wrong on the way

- **First 2023 LP attempt** failed on the read-side column name (§3.2) after writing the program, its five revisions and 294 projects. The rollback script removed them cleanly.
- **`nohup … &` inside a backgrounded shell** was killed when the wrapper exited, leaving 2023 OO-1 loaded to two of five stages. Rolled back — and the rollback then left **2 work items and 4 locations** behind, because the loader stamps `ComponentCostFK = 0` on work items with no matching cost row and the script reached work items only through their component. Fixed to collect by stage `DataImportProgramId` as well; the 6 rows were removed by id. The database also carries **33 other `ComponentCostFK = 0` work items and 57 orphan locations from the 2024 server load** — pre-existing, left alone, recorded here.
- **A pathspec-less commit** in the backend repo swept in the maintainer's already-staged `migration_old.py`. Reverted and redone with an explicit pathspec; that file is back to staged-and-uncommitted, as found.

## 7. What this load does not do

It does not link the children or bring the Lump Sum parents onto the model — that is the SQL migration's job, and the loader's only contribution to it is carrying the notes. It does not touch `ProjectType = 'NULL'` (the reference writes it, on purpose; the migration flips only what it owns) or the code-vs-name `ComponentType` artifact on the ~353,000 rows outside the Lump Sum parents. See `MYPS_LEGACY_LS_MIGRATION_2026-09-14.md` for the migration that follows this load.
